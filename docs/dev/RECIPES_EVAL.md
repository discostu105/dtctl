# Recipes eval — does the recipe book make agents better?

> Executions of the §6.1 eval from [RECIPES_CONCEPT.md](RECIPES_CONCEPT.md),
> run 2026-07-18 against one live dev tenant. Environment details are
> anonymized per the project privacy rule; service names are replaced with
> neutral labels. The first eval below was ad-hoc (two arms, hand-driven);
> the [second eval](#second-eval--repeatable-22-matrix) reran the question as
> a repeatable 2×2 matrix using the committed harness in
> [test/evals/recipes/](../../test/evals/recipes/).

## Design

Two arms, identical prompts, identical model (Sonnet), fresh agent per run:

| Arm | Binary | Knowledge |
|---|---|---|
| A (control) | dtctl built from `main` (no recipes feature) | generic Dynatrace skills only |
| B (recipes) | dtctl from `feat/recipes` | same skills **plus** a recipe book generated by `recipes discover` (52-recipe example pack), bootstrap hint "start with `dtctl recipes`" |

Because both arms had the generic Dynatrace skills available, arm A is
effectively §6.1's *arm 1/2* (static knowledge) and arm B is *arm 3* (full
recipe book) — the comparison measures the **marginal value of per-environment
verification**, not of documentation in general.

Every dtctl invocation went through a logging wrapper (call count, exit code,
full output captured). Six investigation tasks, each run once per arm, ≤12
dtctl calls allowed. Ground truth was established beforehand by direct
queries.

Tasks: (1) top ERROR-log sources in 1h; (2) highest-p95 service;
(3) RUM present? event volume in 24h; (4) GenAI models + token consumption in
24h; (5) **the trap**: complete 2h log count of a named multi-instance
service whose logs are service-stamped on only ~6% of records — the naive
`dt.smartscape.service` filter undercounts 20×; (6) security posture:
attack detections (absent on this tenant) + compliance scanning (present).

## Results

Correctness (against ground truth):

| Task | A (control) | B (recipes) |
|---|---|---|
| 1 error sources | ✅ | ✅ |
| 2 p95 service | ✅ | ✅ (cross-verified via 2 recipes; caught a metric-rollup artifact) |
| 3 RUM volume | ✅ | ✅ |
| 4 GenAI tokens | ✅ | ✅ (single recipe call) |
| 5 log-count trap | ✅ (found the OTel `service.name` path) | ❌→✅ **UNKNOWN on first run; correct after `resolve scope` shipped** (see below) |
| 6 security posture | ✅ | ✅ |

Objective metrics (first run, 6 tasks per arm):

| Metric | A (control) | B (recipes) |
|---|---|---|
| dtctl calls | 24 | 38 |
| errored calls | 3 | 5 |
| empty-result calls | 5 | 1 |
| scanned bytes, task 6 (measured) | ~2.07 GB | ~0.20 GB |
| scanned bytes, task 5 (measured) | ~4.15 GB | n/a (failed) |

## Findings

1. **No silent-wrong answers in either arm.** The trap task's failure mode
   (reporting the 20×-undercounted number as complete) did not occur: arm A
   found an alternate complete path; arm B *knew* the field was partial from
   `facts.fieldCarriage` and refused to report the naive count. The recipe
   book's honesty machinery worked exactly as designed — knowledge-wise.

2. **A strong model with good static skills is a strong control.** On five
   of six tasks the control arm was correct and *cheaper in calls* (recipes
   add ~2 bootstrap calls per session: `recipes` + `describe recipe`). The
   concept's efficiency claim (§6) is **not** confirmed as a call-count win
   on friendly tasks against a capable model.

3. **Where the book pays is proving absence, and it pays in scan cost, not
   calls.** On the security-posture task both arms answered correctly, but
   the control proved "no detections" by brute force — 7-day scans over
   millions of records (~2.07 GB measured) — while the recipes arm read the
   classified `disabled:` entries + `absent:` capabilities and spent one
   confirming query (~0.20 GB, ~10× less). Negative knowledge is consumption
   savings.

4. **Knowledge without mechanics loses to mechanics without knowledge.** The
   first-run trap-task failure is the sharpest result: the recipes agent
   correctly diagnosed the partial-carriage trap from the book, was pointed
   at `resolve scope` by the recipe's own param description — and the
   command didn't exist (it had been cut from the first implementation
   slice). It then burned its remaining budget re-deriving the
   service→pods topology hop by hand (smartscape traverse syntax errors)
   and honestly answered UNKNOWN. Meanwhile the control arm found that this
   OTel-native tenant carries `service.name` directly on logs — a complete,
   cheap path the generator wasn't measuring. Both halves became fixes:
   `resolve scope` now exists (hop widening as one command), and the
   carriage battery measures `service.name` on logs, with SERVICE→logs
   scoping choosing the direct filter wherever its measured carriage ≥ 0.5.
   A re-run of the trap task with the fix produced the correct count in 11
   calls: the agent read the coverage warning from `resolve scope`, used the
   emitted pod filter, and added a `service.name` fallback for an instance
   with no topology edges — knowledge and mechanics finally composing.

5. **Follow-up suggestions and stamps behaved as specified** (envelope
   `suggestions` carried drill edges; every `--recipe` execution refreshed
   its stamp; a disabled recipe executed with its evidence as a warning).

## Honest limitations

- One tenant, one model, one trial per cell — directional, not statistical.
- The tenant is OTel-native and "friendly"; the concept's hard cases
  (mixed-era fields, OneAgent-only populations) are underrepresented.
- Arm B's prompt hinted at the bootstrap call; arm A's hinted at
  `dtctl commands`. Symmetric, but hint wording was not ablated.
- Token usage per run was not captured; calls and scanned bytes stand in.

## Verdict for §8 phasing

The facts/scoping layer (phase 1) and the negative-knowledge channel earn
their keep on measured scan savings and trap protection; the recipe *index*
mattered less against a strong model on friendly tasks. The phase-3 gate
(§6.1: full book must beat pack-as-markdown) remains open — this run
compared against skills, not against the pack rendered as static text, and
should be repeated on a mixed-era tenant with the trap-class tasks weighted
higher.

# Second eval — repeatable 2×2 matrix

The first eval left two dimensions unresolved: it was not repeatable
(hand-driven subagents, scratchpad scripts), and it never varied the
dynatrace-for-ai skills — both arms had them, so the marginal value of the
skills themselves was unmeasured. The harness in
[test/evals/recipes/](../../test/evals/recipes/) fixes both: four variants
(recipes × skills, fully crossed), six tasks, one fresh headless `claude`
agent per cell (Sonnet, `--output-format json`, Bash-only, web access and
subagents disallowed), isolated `CLAUDE_CONFIG_DIR` per run for skill
visibility, a logging dtctl wrapper, per-batch ground truth, and automated
scoring with a SILENT_WRONG verdict for the trap task. Scan cost is
re-measured per agent query via `--metadata=scannedBytes`.

Two batches ran on 2026-07-18: **matrix-1** (full 4×6 = 24 runs), then
**matrix-2** (12 runs: t1/t3/t6 re-run after task-wording fixes — see
finding 2).

## Results

Matrix-1 (original wording), per variant over 6 tasks:

| | base | skills | recipes | recipes-skills |
|---|---|---|---|---|
| correct | 3/6 | **6/6** | 5/6 | 5/6 |
| dtctl calls | 50 | 34 | 33 | **29** |
| empty-result calls | 4 | 2 | 1 | **0** |
| agent turns | 49 | 50 | **35** | **29** |
| tokens in, uncached (k) | **95** | 135 | 167 | 171 |
| tokens in, cache-read (M) | 1.53 | 1.68 | 1.35 | **1.22** |
| tokens out (k) | 14.6 | 11.4 | 13.9 | **8.3** |
| wall time (s) | 250 | 192 | 200 | **141** |
| — of which dtctl (s) | 13.7 | 10.4 | 8.1 | 9.3 |
| cost (USD) | 1.25 | 1.49 | 1.62 | 2.07 |

Matrix-2 (t1/t3/t6, disambiguated wording): **12/12 correct across all four
variants** — calls: base 34, skills **12**, recipes 17, recipes-skills 20;
wall seconds: base 137, skills 90, recipes **84**, recipes-skills 87;
uncached input tokens (k): base **43**, skills 74, recipes 87,
recipes-skills 113; output tokens (k): base 7.4, skills 4.9, recipes
**4.7**, recipes-skills 5.1.

## Findings

1. **The bare model is the danger zone; any curated knowledge fixes it.**
   All three matrix-1 failures in `base` were *silent wrongs* — confidently
   delivered bad numbers: a 2h default window reported as "last 1 hour"
   (dtctl silently accepted `--default-timeframe-start -1h`, which the API
   ignores — a real dtctl UX gap this eval surfaced), a metric-derived
   approximation (229) reported as the RUM event count (~63k), and a
   default-window security count reported as 7 days. Every arm with skills
   and/or recipes avoided all three. This is the strongest argument that
   *some* knowledge layer must ship — and the weakest for recipes
   specifically, since generic skills already provide it.

2. **Ambiguous questions make verified knowledge look wrong.** Both recipe
   arms "failed" t6 in matrix-1 by *measuring the true raw compliance count
   and then deduplicating* re-scan repetition (following the book's own
   KSPM recipe pattern) — a defensible, arguably better answer scored WRONG
   by a raw-count rubric, and four arms produced four distinct defensible
   numbers. After the task pinned "raw event count", all arms converged
   (12/12). Eval-methodology lesson: score verdicts are only as meaningful
   as the task wording is precise.

3. **Recipes' measured wins are query precision and empties, not calls or
   dollars.** On book-covered tasks the recipe arms answered in 2–3 calls
   (t1/t3/t4) with near-zero waste (0–1 empty results vs 4 for base) and the
   fewest agent turns. The sharpest number: t4 (GenAI tokens) scanned
   **~0.0 GB with recipes vs 6.4 GB with skills** — the verified recipe is
   narrow where the skills-guided query brute-forces spans. Per-run dollar
   cost was *highest* for recipe arms (the briefing + `describe recipe`
   context is not free).

4. **The negative-knowledge scan win did not reproduce on t6 this round.**
   The clarified t6 mandates a raw 7-day count, which costs ~10 GB of scan
   no matter what you know; arms differed only in how many multiples of
   that floor they burned (skills 1×, recipes 2×, base/recipes-skills 3×).
   The first eval's 10× absence-proving savings remains real but applies to
   "is X present?" questions, not "count everything" questions.

5. **The trap did not discriminate at this model tier.** All four arms
   passed t5 (complete multi-instance log count) — Sonnet finds the
   OTel `service.name` path even bare. The book's carriage facts and
   `resolve scope` were used by the recipe arms (9–10 calls) but base got
   there in 7. On a OneAgent-only tenant without the `service.name`
   escape hatch, this task should separate the arms; that tenant is the
   right next battleground.

6. **Latency is won by knowledge, tokens are split.** End-to-end latency
   drops with every knowledge layer (matrix-1 batch wall time: base 250s →
   recipes-skills 141s; matrix-2 per-task ~46s bare vs ~28s with recipes) —
   and essentially none of it is dtctl execution (< 14s per batch; model
   thinking dominates). Tokens go both ways: *uncached input* grows
   monotonically with knowledge (95k → 171k per matrix-1 batch — briefings
   and skill references are real context), while *output* tokens shrink
   (14.6k → 8.3k — less flailing, fewer retries). Since output tokens cost
   ~5× input, the output savings offsets part but not all of the input
   overhead: dollar cost still ranks base < skills < recipes <
   recipes-skills.

7. **Skills and recipes are largely redundant on a friendly tenant.**
   `recipes-skills` was the most precise (0 empties, fewest turns) but not
   more correct than `skills` alone, and the most expensive. The
   combination's value should grow with tenant weirdness (mixed-era
   fields, absences, partial carriage) — which this tenant mostly lacks.

## Repeatability

`test/evals/recipes/`: `build.sh` (pins both binaries by commit),
`env.sh` (git-ignored tenant parameters), `run.sh -v <variants> -t <tasks>`
(any subset, any batch), `score.py <batch> [--measure-scan]`. Per run it
records correctness verdict, dtctl calls/errors/empties, agent turns, token
usage (uncached input, cache reads, output), wall/API/dtctl latency, dollar
cost, and (opt-in) scanned bytes. Ground truth is re-measured per batch, so
results are comparable across time on the same tenant; run artifacts stay
outside the repo (they contain tenant data).
One trial per cell is still directional — batches are cheap (~$1–2 per
variant) so repeat runs are the intended way to firm up any of the numbers
above.

## Follow-ups this eval generated

- dtctl: `--default-timeframe-start` silently accepts relative values like
  `-1h` and the API ignores them (finding 1) — should validate or support
  relative syntax.
- Re-run the matrix on a OneAgent-only / mixed-era tenant where the t5
  trap has no `service.name` escape hatch (finding 5) and add an
  absence-question variant of t6 (finding 4).
- Phase-3 gate (§6.1) still open: add a fifth variant — the pack rendered
  as a static skill — to separate "verified per-environment knowledge"
  from "more Dynatrace text in context".
